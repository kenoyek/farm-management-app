## Phase 2 private autosave delivery

Migration `010_formulation_drafts.sql` adds one private working draft per user and organization, with RLS, strict structural validation, tenant-checked ingredient/profile/recipe references and optimistic revision matching. Other organization members, including administrators, cannot read that user's draft through the runtime role. Auditors cannot save drafts. A stale insert/update returns HTTP 409; parallel writes cannot silently replace one another. Writes also bind to the authenticated account that loaded the draft, so an account switch in another tab cannot save old content under the new account.

Feed studio automatically restores and saves the recipe name, batch weight, ingredient lines/bounds/availability, selected profile and cloned-version link. It permits incomplete numeric editing states, but never stores approval status or calculated compliance as part of a draft. Restoring always resets approval selection to Draft and requires fresh calculation. Immutable recipe versions remain a separate explicit save action.

The editor waits for its saved state before accepting changes. Saves are debounced and serialized; changes made during a pending request are queued. Navigation flushes pending changes. A tab-local session recovery copy is scoped by organization and authenticated user; it survives reload/navigation in that tab if a request fails. Closing a tab clears its browser recovery data; unsaved changes trigger a browser warning where supported. If browser recovery storage is unavailable, server saves still work and the user is told to keep the page open until saved. This does not guarantee offline access or background delivery after closing a browser.

On conflict, automatic writes stop and local edits are retained. Users can download a JSON copy and explicitly confirm loading the server's draft; there is no automatic overwrite option. The original recovery revision is retained across reloads so stale local data cannot become a new trusted base accidentally. A lost response is recognized only when a fresh authenticated read proves the server already holds exactly the submitted content. Failed initial loads keep editing disabled and offer a retry rather than overwriting an unseen draft.

Current validation: 78 TypeScript/domain/database/controller tests and six production-mode Chromium workflows; strict types, lint and build. The new tests cover privacy/RLS, role loss, foreign references, strict draft-only payloads, concurrent writers, queued edits, interrupted saves/recovery, storage unavailability, response loss, account changes, stale load cancellation, and browser conflict/download/reload controls. Expanded nutrients and qualified reference-catalog reconciliation remain outstanding Phase 2 work.

## Reviewed stage-specific ingredient rules and profile revisions

Feed studio → Specifications now lists reviewed requirements with nutrient limits, declared bases, source evidence, reviewer identity and review date. Assigned nutritionists can register a profile or append a new revision. Current versions are shown by default; history reveals older versions and JSON downloads preserve exact profile evidence. Every revision requires explicit review confirmation in the interface. Competing revisions have one winner; stale revisions are rejected. Existing formula drafts/versions retain their selected historical profile until the user deliberately changes it.

A profile may define up to 100 exact ingredient-reference rules, each with explicit minimum/maximum inclusion percentages and its own review evidence. Positive minima require inclusion even if the ingredient was omitted from a manual recipe; equal bounds fix inclusion; maximum zero excludes the reference. **A nonempty rule list is an allowed list**: every permitted ingredient revision must be listed, including unrestricted 0–100% references. Unlisted references and replacement quotations do not inherit authorization by name or lineage. Revise the profile to review a new ingredient/quotation UUID. Profiles without rules retain the existing open selection behavior, subject to all ingredient review/species/stage/basis checks. Rules are not inferred from staged workbook ranges or aliases.

Migration `012_profile_rules.sql` adds immutable profile rule JSON and revision lineage to the existing tenant-RLS table. Keeping all rules in the inserted profile row prevents later rule additions from changing an existing approval. A validation trigger independently checks the reviewer, shape/unique exact UUIDs, same-organization visibility, approved ingredient status, species/stage/bases and bounds. Profiles cannot weaken ingredient inclusion limits or contain bounds that cannot total 100%. Original profiles receive revision 1 and an empty rule list without changing old recipe results. Runtime UPDATE/DELETE remains prohibited.

Manual calculation reports rule violations and blocks approval. Real HiGHS runs intersect profile, ingredient, scenario and available-quantity bounds; missing mandatory references and unlisted candidates are refused, conflicting bounds remain infeasible, and solved allocations are independently checked against profile rules. New saved recipe results retain the full profile snapshot. Optimizer request model 2 additionally stores the profile and selected ingredient snapshots, so changing a reference or profile cannot rewrite the evidence of a previous run. Numerical results remain planning/review evidence, not manufacturing authorization.

## Phase 3 saved recipe comparisons and mixing reports

Feed studio → Recipe library now compares two to four immutable saved versions with an explicitly selected baseline and common comparison batch. It shows saved status/batch/inclusion totals, historical NGN/kg and common-batch costs, signed decimal cost deltas, stored nutrient results and each recipe's own specification checks. Common costs multiply the recorded four-decimal unit result; rounding can differ from the original saved batch total. Ingredient rows match exact UUIDs, so a new quotation/revision is a separate row rather than a guessed alias. Unknown prices/nutrients/deltas remain unknown; incomplete inclusion totals are never normalized. The library currently lists the latest 100 versions.

Nutrient deltas are available only when every version has matching recorded species, stage, nutrient basis, energy system and phosphorus basis. Missing/incompatible contexts withhold all nutrient deltas and show a warning; cost comparisons remain explicitly historical. Different profile IDs are called out because compliance is against each recipe's own saved specification. A common comparison batch is a planning view: it neither transfers approval/availability to that resized batch nor saves a new formula, reserves stock or posts costs. Comparison CSV includes full IDs, warnings, original/common batches, own limits/checks, deltas and exact-reference allocations. Complete optimizer-run scenario comparison is still unfinished.

Each saved version can be downloaded as CSV or a real four-sheet .xlsx workbook: Mixing sheet, Nutrients, Reference audit and Specification. Reports use the original saved batch and saved ingredient/price/nutrient evidence, not current references or refreshed quotations. They include version/organization UUIDs, timestamps/status, nullable source/quotation/reviewer evidence, scenario bounds/availability, profile restrictions and saved validation issues. Draft/pending/rejected versions carry explicit NOT APPROVED labels; approved versions identify historical approval without claiming current manufacturing release. New saves additionally record the authenticated saving actor UUID; older versions report that actor as unrecorded. Model-1 recipes can use their immutable referenced profile when an embedded profile snapshot is absent. Incomplete legacy report evidence returns an error without rewriting history.

Exports are current-membership authenticated and organization-scoped under existing RLS; auditors may download reports. Mixed-tenant comparisons fail atomically with no partial data. Responses are private/no-store with attachment names based on the UUID. The report and response include a SHA-256 of normalized saved-report data; this identifies the evidence, not workbook file authenticity. CSV neutralizes formula-like strings. The Python writer forces every string to text, preserves numeric zeros and blank unknowns, replaces XML-incompatible text characters, and retains monetary values as decimal text to avoid Excel precision loss. It writes numeric weights to six decimal places. It has bounded stdin/output (2 MiB each), at most five sheets, 2,000 rows/sheet, 32 columns, 20,000 cells, 4,000 characters/cell, Linux CPU/address-space limits and a 10-second server timeout. Server concurrency is capped at two writers and exports use process-local per-account rate limits. Missing Python dependencies yield a controlled error; CSV remains available. Worker tracing includes the new script. No new database privileges or migrations are required.

## Phase 3 optimizer diagnostics and immutable run history

Formulator now retains the latest submitted run's evidence until its inputs change. It shows the saved run UUID, actual solver/precheck status, every effective inclusion bound and its scenario/ingredient/profile/availability sources. Prechecks explain contradictory bounds, minimum totals above 100%, maximum-total capacity shortfalls and individual nutrient limits outside attainable ranges. Each nutrient range is calculated under the unchanged ingredient bounds and sum(x)=1, explicitly without the other nutrient limits. It is a necessary condition, not a joint feasibility or nutrition-safety proof. Coupled conflicts that pass these tests still go through real HiGHS and remain infeasible if the full model cannot be solved. No constraints are automatically removed or relaxed, and no infeasible result receives a fabricated allocation/cost.

Optimal runs additionally retain independently recomputed total-inclusion error, maximum inclusion-bound violation and objective error/tolerance, alongside stored nutrient compliance and binding constraints. Scientific/reference/quotation gates remain in force before a run. Only feed editors may execute optimization; all current organization members, including auditors, can inspect historical runs. New request model 3 retains original scenario inputs and ingredient/profile snapshots; result diagnostic model 1 adds the evidence above. Old records are not rewritten.

Feed studio → Optimizer history lists the latest 100 runs, with name/UUID search, status filters, historical costs, full outcome details and original request/reference JSON. The list projects summary fields rather than transmitting every reference snapshot. Detail/download access is current-member tenant RLS scoped; forged organization IDs or outsiders see no run. JSON download retains the original row's request/result. Legacy runs without snapshots or detailed checks are labeled explicitly; current references are never substituted as historical evidence.

**Load scenario as draft** requires an explicit replacement action, a ready private draft and current feed-editor access. It restores original batch/profile/reference IDs, scenario bounds, availability and any original cloned-recipe parent. An optimal saved allocation is used only when its IDs/counts/percentages/total are structurally valid; otherwise original input percentages are restored. Same-organization references are checked before restoration is offered. Approval/result fields are discarded, saving an immutable formula remains a separate action, and fresh calculation/review/quotation checks apply. No stock reservation, manufacturing event or approved recipe is created by viewing/restoring a run.

The Python worker now validates the complete bounded protocol: up to 100 variables, seven nutrient rows, finite positive costs, consistent matrix dimensions, ordered fractional bounds and finite nonnegative nutrient values/ranges. It has 256 KiB input/output limits, single BLAS/OpenMP threads, a 512 MiB address-space cap, 10/11-second CPU limits, an eight-second HiGHS time limit and a 20-second server watchdog. Node limits concurrent solves to two and applies process-local per-user attempt limits. Worker errors/stderr are not exposed as raw system details. Optimal responses require the exact finite allocation dimension and independently checked objective; nonoptimal responses cannot carry allocations. This is resource hardening, not a public deployment/security certification.
